# Alternate message body recovery

**2026-09-05 integration update:** The runtime decoder and all three reader paths are now implemented and installed in the actual engine. See [current implementation and live-data limits](LIVE_CONNECTION_AND_REPLY_REPAIR.md#full-message-body-recovery). The user subsequently authorized real Messages reads. The latest 500-row and 200-archive samples contain only marker text in attributed-only bodies; they do not prove recovery of live readable prose. Public text fixtures verify that capability. The sections below retain the earlier experiment and deferral chronology, not current integration status.

M5 still excludes messages whose plain-text field is empty even when `attributedBody` contains text. The next implementation must feed the same exact recovered string to notification ingestion, the conversation picker/history, and assistant reads. A decode failure must be visible as unavailable content instead of silently deleting a message. Plain text remains the preferred source when present. No live chat.db will be used for development evidence.

Before adding a runtime dependency, validate the data-only `pytypedstream==0.1.0` parser against pinned public message fixtures, including long text, emoji, formatting, links and multipart bodies. The probe retains the untouched wheel under `vendor/joat-message-parser-probe`, verifies its PyPI SHA-256, and imports it there. It does not install it into JOAT's runtime. The probe also inserts those blobs into a synthetic database and measures current production omissions. Failed formats must remain explicit; do not take arbitrary printable strings from archive bytes or attribute metadata as message text.

Primary sources checked 2026-09-05 UTC:

- [Apple NSUnarchiver](https://developer.apple.com/documentation/foundation/nsunarchiver) is Apple's legacy archive API. The source examined does not provide a supported Messages database schema; native object unarchiving is not assumed to be a safe drop-in decoder.
- [pytypedstream maintainer README](https://github.com/dgelessus/python-typedstream) documents the distinction between typedstream and the binary property lists used by keyed archives. Quote: “no native Mac APIs are used”. Its published distribution identifies `LGPL-3.0-or-later`; retain its notices and use the unmodified dependency rather than copying parser code into JOAT.
- [pytypedstream API source](https://github.com/dgelessus/python-typedstream/blob/master/src/typedstream/archiving.py) describes `GenericArchivedObject`, ordered typed fields and a single-root decoder. [NSString implementation](https://github.com/dgelessus/python-typedstream/blob/master/src/typedstream/types/foundation.py) decodes its string payload as UTF-8.
- [imessage-exporter message-body parser](https://github.com/ReagentX/imessage-exporter/blob/4d90fc8d20a745c0a8acc1e01c0631c4bab89cb4/imessage-database/src/tables/messages/body.rs) explicitly handles `message.attributedBody` through a typedstream parser. Its [public fixtures](https://github.com/ReagentX/imessage-exporter/tree/4d90fc8d20a745c0a8acc1e01c0631c4bab89cb4/imessage-database/test_data/typedstream) supply independent format samples. This is third-party reverse-engineering evidence, not an Apple or Even Realities contract. The upstream GPL license applies to the retained upstream material; no upstream implementation is copied into app source.

## Completed experiment, not an integrated repair

Job `job-mtnuub3n-fefc76dc` completed with exit 0. Root inspected its output after the completion notification. The [retained result](evidence/remediation/message-body-parser-probe.json) has SHA256 `72418a6bc8dd332759c001d121d6f5b01e1801fb90a1ebf7907239461f380a0e`.

- All nine pinned archive samples decoded: eight yielded nonempty text, one was the intentional blank sample. The long sample yielded 2,359 characters. Two simple samples matched independently stated upstream expected text; the other seven have structural decode results and text hashes, not independently asserted full-text equality.
- The synthetic database contained those nine attributed-body-only rows. Current production code exposed zero conversations, zero history entries and zero new notifications. Thus the eight nonempty decoded samples are omitted by the existing production read paths.
- Production `imessage.py` still matches the probed SHA256 `b5802178826e87726896d2707955b2b9d4a6083cde3a001d8dd8376f931cbb65`. This is a reproducible current-source gap on synthetic data; it does not establish which real messages on the user's Mac use these formats.
- No runtime dependency was installed, no production decoder was added, and no live Messages database, simulator or glasses was used by this experiment.

Runtime integration is deferred while the requested UI stabilization is prioritized. Decoder error handling, regression tests, missing conversation-picker pagination, simulator and physical G2 acceptance remain incomplete. Process success is not repair acceptance.
